## Цель и договорённости

Сделать размещение предметов и перестановку сумок предсказуемыми мышью и
пальцем в Mushroom Battles и Meat Master. Игрок должен видеть результат до
отпускания и понимать отказ без прерывания игры. Этот документ в core —
канонический план для обоих потребителей.

**Требования пользователя:** учесть отзыв о невозможности положить предмет
между двумя сумками, неприятном управлении и переносе сумок только через
плашки; объяснять отказ на поле подсветкой и коротким текстом, без попапа.

**Дополнение пользователя:** определить поведение в core, чтобы оба проекта
использовали одинаковые улучшения; необходимый рефакторинг входит в план.
Критерий успеха: обе игры используют один механизм взаимодействия и проходят
одинаковые проверки.

**Новые требования пользователя (2026-10-11):** убрать постоянные кнопки
Move bags / Rotate / To Storage / Auto-place / Sell / Cancel; показывать
перемещаемый предмет или сумку под указателем; вместо переключателя
предметы/сумки захватывать сумку за любую её свободную доступную клетку.
При успешном переносе сумки её предметы переходят в Storage.

**Предложения плана:** возврат и продажа через зоны drop, контекстные действия
вместо панели; для предметов на стыке сумок — правило пересечения старого
покрытия сумки, описанное ниже. Способ определения содержимого и доступ
к полностью заполненной сумке — проектные решения, а не требования из отзыва.
Новая модель заменяет первоначальный режим сумок и блокировку переноса из-за
потери покрытия предметами.

Вне текущего объёма: баланс, бой, магазин, каталог арта, монетизация и общий
редизайн приложения. Механику покрытия сумками не менять без воспроизведения
ошибки и отдельного обоснования.

## Основания и ограничения анализа

Анализ исходников показал:

- `validation.js`, `validateItemCoverage`: доступные клетки всех активных сумок
  объединяются. Предмет может пересекать их границу, если каждая клетка покрыта.
- `create-configured-gameplay-screen.js`, `cellDrop`: клетка сброса становится
  началом предмета; смещение точки захвата не учитывается.
- `ArtifactGridBoard.js`: поддерживает `placementPreviewForCell`, но
  проанализированный игровой экран его не передаёт.
- `BackpackZone.js`: активные сумки перемещаются через плашки под полем.
- Тап по предмету вызывает `unplace`; выбор в Storage вызывает `autoPlace`,
  который при отсутствии позиции возвращается без объяснения.
- `useTouch.js` существует, но не подключён к проанализированному экрану.
  Простого подключения недостаточно: отличаются поля состояния и расчёт drop.

Все перечисленные core-файлы находятся под `vendor/backpack-game-core/src/`:
геометрия — `modules/loadout/`, экран — `vue/configured/`, компоненты —
`vue/components/`, обработчик — `vue/composables/`.

Аудит выполнен на checkout core `d0ec2cf43b2ae89e6e688ad3e1ce284f7dcc3953`.
База ветки плана Meat — `e2ad6d53c11be2532f92e51fb4676b96902b7ee4`, её
записанный pointer core — `1b0976eb865506cd8dd27b47c2cf7a46460d1d67`.
Перед реализацией обязательно сверить выводы с выбранной согласованной базой;
текущий checkout nested core не включать случайно в документационный PR.

Конкретный отказ со скриншота и управление в Telegram WebView ещё не
воспроизведены. Возможные причины — пустая клетка между сумками, другой anchor
при сбросе или ошибка интерактивной области. Не считать гипотезы доказанными.

## Общий контракт и рефакторинг core

Разделить общий механизм на три уровня:

1. `modules/loadout`: чистый расчёт позиции, клеток фигуры, покрытия и коллизий.
   Единый результат проверки: допустимость, anchor, footprint, конфликтные
   клетки и стабильный код причины; без локализованного текста и DOM.
2. `vue/composables`: общий контроллер выбора и перемещения с состояниями
   idle → selected/dragging → preview → committing → idle/selected. Он хранит
   row/instance ID, источник, rotation и смещение захвата, обрабатывает отмену,
   блокирует конфликтующие сохранения и принимает adapter сохранения.
3. `vue/components` и `vue/configured`: общие bindings сетки, точного preview,
   контекстных действий, прямого захвата сумок и немодального объяснения отказа.
   Продукты передают каталог, локализованные подписи, визуальную тему,
   tutorial/haptics callbacks, сохранение и явные policy-настройки.

Публичный API экспортировать через фасады `modules/loadout` и
`vue/composables`/`vue/components`; типы обновить вместе с реализацией. Названия
новых сущностей выбрать после аудита существующих prep planners: расширять
их, а не создавать второй независимый валидатор.

**Необходимый рефакторинг:**

- Свести `draggingRowId` Meat и `draggingArtifactId`/`draggingItem` Mushroom к
  одному контракту экземпляра предмета. Дубликаты одного artifact ID не должны
  путаться; хранение данных и API обоих продуктов сохраняются через adapters.
- Переработать или заменить существующий `useTouch` общим контроллером: не
  оставлять одновременно два владельца drag, два расчёта anchor или два drop.
- Meat configured screen и Mushroom prep/shop wiring подключить к одному
  контроллеру. Из Mushroom удалить только ставшие дубликатами обработчики;
  продуктовые покупки, fusion, undo, tutorial, haptics и серверные особенности
  сохранить через callbacks/ports и проверить на регрессии.
- Переиспользовать existing preview и prep planners, согласовать их с серверным
  валидатором; preview не должен обещать позицию, которую сервер отвергает по
  геометрическим правилам.
- Общие классы и структура состояний находятся в core; продуктовые цвета,
  артефакты и тексты — у потребителей. Не создавать Meat/Mushroom ветвления
  по названию игры внутри контроллера.
- Предусмотреть переход совместимости для старого `useTouch` и событий сетки:
  тонкий adapter либо атомарная миграция обоих потребителей. Удалять старые
  экспорты только после проверки всех consumers. Проверить неигровые/read-only
  использования сетки: replay, summary, catalog не должны получить drag.

В Mushroom уже вызывается core `useTouch` из `web/src/main.js`, а
`web/src/components/prep/BackpackZone.js` передаёт placement preview. Meat
использует configured screen с другим wiring. Поэтому наличия общего
компонента недостаточно: обязательна миграция обоих путей ввода.

## Целевое поведение

### Предметы и действия

1. В idle видны Storage, поле и магазин. Постоянной панели действий и
   переключателя предметы/сумки нет. Инструкция появляется при первом
   использовании/обучении; ошибка — коротким сообщением рядом с полем.
2. Тап/клик выделяет предмет в Backpack или Storage; следующий тап на поле
   задаёт позицию. Выбор сам по себе не перемещает и не продаёт предмет.
3. Во время drag изображение предмета или сумки следует за указателем,
   сохраняет точку захвата и поворот. Snap-preview на поле отдельно показывает
   полную форму, допустимость и конфликтные клетки. Ghost не перехватывает
   ввод и исчезает при завершении/отмене. На touch проверить видимость рядом
   с пальцем, не нарушая точности точки захвата.
4. Возврат предмета в Storage — drop в видимую область Storage. Продажа —
   drop в отдельную зону продажи, которая появляется при переносе подходящего
   предмета и показывает цену возврата до отпускания. Проверять её границы и
   отделить от Storage, чтобы промах не приводил к продаже. Сохранять серверные
   ограничения продажи и доступный вариант без drag в контекстном меню.
5. Поворот — клавиша R во время desktop drag; на touch и при выборе без drag —
   небольшое действие ↻. Auto-place и остальные доступные операции находятся
   в меню ⋯ выбранного предмета. Показывать только применимые действия.
6. Cancel — Escape или тап вне поля и активных зон/контекстных действий.
   Контекстные ↻/⋯ имеют постоянное место у края поля и не закрывают клетки.
   Их появление и исчезновение не меняет координаты поля и зон drop.
7. Невалидный drop оставляет подтверждённую раскладку и не отправляет заведомо
   ошибочный запрос. Причина («Занято», «Нет клетки рюкзака», «Выходит за поле»)
   показывается без модального окна и обозначается не только цветом.
8. Сообщение после отказа остаётся примерно две секунды, не перекрывает цель
   и обновляется без очереди при повторении. Нет места для Auto-place — такое
   же понятное объяснение. Ошибка сервера восстанавливает подтверждённое
   состояние. Preview и сервер используют одинаковые правила.

### Сумки: захват за свободную клетку

- Pointer down на предмете выбирает предмет. Pointer down на свободной
  доступной клетке перемещаемой сумки подготавливает перенос этой сумки;
  drag начинается только после порога движения. Обычный тап ничего не
  освобождает и не сохраняет. При уже выбранном предмете обычный тап по
  свободной клетке размещает этот предмет; перенос сумки требует drag.
  Hit test учитывает реальную маску сумки и
  footprint предметов, а не прозрачность арта или прямоугольник изображения.
  Пустота вне сумок и отверстия в их форме не являются точками захвата.
- Сумка следует за указателем с сохранённым смещением захвата. Прежнее
  положение сохраняется до успешного drop. Нет отдельного режима Move bags.
- **Предлагаемое правило содержимого:** в Storage целиком переходят все
  размещённые предметы, чей footprint пересекает хотя бы одну доступную клетку
  старой позиции этой сумки. Предмет на стыке двух сумок переносится целиком
  один раз по instance ID. Остальные предметы сохраняют позиции. Перед
  сохранением проверять покрытие оставшихся предметов в итоговой раскладке.
  Пример: длинный предмет занимает A и B; перенос A отправляет его в Storage,
  даже если часть предмета находится в B. Не вводить скрытого владельца сумки.
- Preview сообщает число предметов, которые уйдут в Storage, и выделяет их
  на старой позиции; никогда не изменяет сохранённые строки при pointer down
  или движении. Не создавать попап подтверждения обычного переноса.
- Drop на допустимую новую позицию сохраняет сумку и освобождение её предметов
  **одной атомарной операцией** с одной revision. Сохранять instance IDs,
  количество и поворот предметов; после refresh результат тот же. Drop на
  прежнюю позицию без изменения поворота — no-op, содержимое не освобождается.
- Invalid drop, сброс вне подходящей зоны, Escape, `pointercancel`, потеря
  capture/фокуса и ошибка сохранения не освобождают содержимое: сумка и все
  предметы остаются в подтверждённом состоянии. Не выполнять последовательные
  unplace-запросы до сохранения сумки. На время commit блокировать конфликтующие
  покупки/продажи/refresh; при revision conflict перечитать авторитетное состояние.
- **Предложение для полностью заполненной сумки:** постоянная небольшая
  доступная метка/граница сумки открывает контекстное меню «Переместить»;
  затем можно выбрать позицию тапом или клавиатурой. Это fallback без режима
  сумок и без зависимости только от long press. Проверить читаемость меток
  соседних сумок и отсутствие перекрытия предметов/клеток.
- Фиксированная стартовая сумка соблюдает действующую product policy: замок и
  короткая причина. Не менять правила продажи/удаления/поворота сумок молча:
  освобождение содержимого в этой итерации относится к переносу; остальные
  операции сохраняют текущие ограничения до отдельного решения.

### Поле и доступность

Доступная пустая клетка и пространство вне сумок визуально различаются.
Выбор, размещение, Storage, продажа, поворот и отмена доступны без drag,
в том числе с клавиатуры и на touch. У контекстных действий есть подписи и
focus states; причины отказа доступны вспомогательным технологиям без
повторного озвучивания на каждом движении указателя. На узком экране зоны
Storage/продажи достижимы при переносе: при необходимости предусмотреть
предсказуемый autoscroll, который не конфликтует с обычной прокруткой.

До редактирования runtime сверить текущие prep planners и API обоих продуктов.
Переиспользовать единую запись loadout, если она уже атомарна; при необходимости
расширить её payload/валидацию вместо цепочки запросов. Core выдаёт план
изменений plain rows, продукт владеет транзакцией. Назначить одного владельца
каждого shared-файла, не редактировать его одновременно.

## Проверки и критерии приёмки

### Новая итерация: обязательны для обеих игр

- [x] **AC16** — Нет постоянной панели и переключателя предметы/сумки;
  ↻/⋯ появляются контекстно, координаты поля и зон drop не меняются.
- [x] **AC17** — Свободная доступная клетка начинает drag своей сумки после
  порога; занятая клетка захватывает предмет, отверстие формы — ничего.
  Полностью заполненная сумка доступна через контекстный fallback без drag.
- [x] **AC18** — Валидный перенос сумки атомарно отправляет пересекающие её
  старую маску предметы в Storage; seam-предмет целиком, дубликаты независимо,
  rotation/instance IDs сохранены. Остальные позиции и статистика корректны;
  refresh и начало боя видят подтверждённую раскладку. No-op не освобождает сумку.
- [x] **AC19** — Отмена/invalid drop/потеря capture/ошибка API/revision conflict
  не дают частично освобождённой сумки или потерянных предметов. Быстрый повтор,
  покупка, продажа и refresh не обходят блокировку commit. Сервер применяет
  ту же геометрию и набор затронутых строк, что preview.
- [x] **AC20** — Storage и продажа выполняются только через допустимые зоны
  либо явные контекстные действия; цена видна до продажи, промах отменяется.
  Поворот, Auto-place, выбор/размещение и Cancel доступны мышью, touch и клавиатурой.
- [x] **AC21** — Арт предмета/сумки следует за точкой захвата и поворотом,
  не перехватывает hit test; preview и предупреждение об освобождении сумки
  видны и не закрывают целевые клетки на 375×667 и 1280×800.
- [x] **AC22** — Обе игры используют общий controller и один core commit;
  обновлены tutorial/локализация/user flows; проходят доменные, controller,
  persistence и browser проверки с durable evidence.
- [ ] **AC23** — Новые жесты, доступность зон и fallback полной сумки проверены
  пользователем в реальных iOS/Android Telegram WebView; эмуляция не заменяет устройства.

### Первая итерация: историческая приёмка и регрессионная база

N1–N4 реализованы. Общий controller определяет захват по доступным клеткам,
показывает арт под указателем и сохраняет смещение захвата при повороте.
Постоянная панель и mode удалены; ↻/⋯ доступны при выборе, меню помещается
на 375px. Полная сумка выбирается доступной плашкой (Enter/Space).

Core вычисляет пересечение **старой** usable mask, целые instance IDs и
no-op. Сервер повторяет расчёт по авторитетным строкам, а продукт сохраняет
сумку и освобождённые предметы одной транзакцией. Переносы фиксированной сумки,
подмена IDs, invalid drop и конфликт revision отклоняются без частичной записи.
Meat сохраняет числовую revision; Mushroom передаёт общий стабильный fingerprint.
Продажа показывает фактический refund; запрет продажи сумок Meat остаётся
продуктовым правилом.

Выявленные и исправленные проблемы:

- Vue computed selection обязана читать reactive selection/drag state перед
  non-reactive pointer веткой: иначе меню сохраняло устаревший выбор.
- Fingerprint Mushroom использует сохранённые размеры существующих строк;
  display mask сумки может отличаться от catalog/persisted dimensions.
  Купленные строки, ещё не добавленные в raw loadout, берутся из buckets.
- SQLite получает writer reservation через IMMEDIATE до чтения revision,
  чтобы конкурентный writer не приводил к read-to-write upgrade SQLITE_BUSY.
  PostgreSQL сохраняет обычный режим транзакций.
- Non-bag rotation сохраняется сервером и при эвакуации. Исторические тесты,
  требовавшие принудительного сброса rotation, приведены к контракту.
- Touch blur с relatedTarget=null не закрывает меню до нажатия действия.
  Pointercancel, Escape и потеря capture очищают весь transient state.
- Desktop Mushroom размещает единственный активный controls instance в
  topbar, mobile — перед полем: Ready остаётся на первом экране без смещения
  клеток при выборе. Проверка полного suite выявила регрессию высоты после
  первоначального переноса controls в loadout column; исправление проверяется
  повторным focused journey.
