## Цель и договорённости

Сделать размещение предметов и перестановку сумок предсказуемыми мышью и
пальцем в Mushroom Battles и Meat Master. Игрок должен видеть результат до
отпускания и понимать отказ без прерывания игры. Этот документ в core —
канонический план для обоих потребителей.

**Требования пользователя:** учесть отзыв о невозможности положить предмет
между двумя сумками, неприятном управлении и переносе сумок только через
плашки; объяснять отказ на поле подсветкой и коротким текстом, без попапа.

**Дополнение пользователя:** определить поведение в core, чтобы оба проекта
использовали одинаковые улучшения; необходимый рефакторинг входит в план.
Критерий успеха: обе игры используют один механизм взаимодействия и проходят
одинаковые проверки. Открытые решения: политика стартовой сумки и перенос
содержимого, обозначенные ниже как предложения.

**Предлагаемые решения:** единый обработчик Pointer Events; точный предпросмотр
формы; выбор и размещение двумя тапами; отдельное действие возврата в Storage;
режим перестановки сумок на самом поле. Это решения плана, а не дополнительные
требования из прикреплённого отзыва.

Вне текущего объёма: баланс, бой, магазин, каталог арта, монетизация и общий
редизайн приложения. Механику покрытия сумками не менять без воспроизведения
ошибки и отдельного обоснования.

## Основания и ограничения анализа

Анализ исходников показал:

- `validation.js`, `validateItemCoverage`: доступные клетки всех активных сумок
  объединяются. Предмет может пересекать их границу, если каждая клетка покрыта.
- `create-configured-gameplay-screen.js`, `cellDrop`: клетка сброса становится
  началом предмета; смещение точки захвата не учитывается.
- `ArtifactGridBoard.js`: поддерживает `placementPreviewForCell`, но
  проанализированный игровой экран его не передаёт.
- `BackpackZone.js`: активные сумки перемещаются через плашки под полем.
- Тап по предмету вызывает `unplace`; выбор в Storage вызывает `autoPlace`,
  который при отсутствии позиции возвращается без объяснения.
- `useTouch.js` существует, но не подключён к проанализированному экрану.
  Простого подключения недостаточно: отличаются поля состояния и расчёт drop.

Все перечисленные core-файлы находятся под `vendor/backpack-game-core/src/`:
геометрия — `modules/loadout/`, экран — `vue/configured/`, компоненты —
`vue/components/`, обработчик — `vue/composables/`.

Аудит выполнен на checkout core `d0ec2cf43b2ae89e6e688ad3e1ce284f7dcc3953`.
База ветки плана Meat — `e2ad6d53c11be2532f92e51fb4676b96902b7ee4`, её
записанный pointer core — `1b0976eb865506cd8dd27b47c2cf7a46460d1d67`.
Перед реализацией обязательно сверить выводы с выбранной согласованной базой;
текущий checkout nested core не включать случайно в документационный PR.

Конкретный отказ со скриншота и управление в Telegram WebView ещё не
воспроизведены. Возможные причины — пустая клетка между сумками, другой anchor
при сбросе или ошибка интерактивной области. Не считать гипотезы доказанными.

## Общий контракт и рефакторинг core

Разделить общий механизм на три уровня:

1. `modules/loadout`: чистый расчёт позиции, клеток фигуры, покрытия и коллизий.
   Единый результат проверки: допустимость, anchor, footprint, конфликтные
   клетки и стабильный код причины; без локализованного текста и DOM.
2. `vue/composables`: общий контроллер выбора и перемещения с состояниями
   idle → selected/dragging → preview → committing → idle/selected. Он хранит
   row/instance ID, источник, rotation и смещение захвата, обрабатывает отмену,
   блокирует конфликтующие сохранения и принимает adapter сохранения.
3. `vue/components` и `vue/configured`: общие bindings сетки, точного preview,
   действий над предметом, режима сумок и немодального объяснения отказа.
   Продукты передают каталог, локализованные подписи, визуальную тему,
   tutorial/haptics callbacks, сохранение и явные policy-настройки.

Публичный API экспортировать через фасады `modules/loadout` и
`vue/composables`/`vue/components`; типы обновить вместе с реализацией. Названия
новых сущностей выбрать после аудита существующих prep planners: расширять
их, а не создавать второй независимый валидатор.

**Необходимый рефакторинг:**

- Свести `draggingRowId` Meat и `draggingArtifactId`/`draggingItem` Mushroom к
  одному контракту экземпляра предмета. Дубликаты одного artifact ID не должны
  путаться; хранение данных и API обоих продуктов сохраняются через adapters.
- Переработать или заменить существующий `useTouch` общим контроллером: не
  оставлять одновременно два владельца drag, два расчёта anchor или два drop.
- Meat configured screen и Mushroom prep/shop wiring подключить к одному
  контроллеру. Из Mushroom удалить только ставшие дубликатами обработчики;
  продуктовые покупки, fusion, undo, tutorial, haptics и серверные особенности
  сохранить через callbacks/ports и проверить на регрессии.
- Переиспользовать existing preview и prep planners, согласовать их с серверным
  валидатором; preview не должен обещать позицию, которую сервер отвергает по
  геометрическим правилам.
- Общие классы и структура состояний находятся в core; продуктовые цвета,
  артефакты и тексты — у потребителей. Не создавать Meat/Mushroom ветвления
  по названию игры внутри контроллера.
- Предусмотреть переход совместимости для старого `useTouch` и событий сетки:
  тонкий adapter либо атомарная миграция обоих потребителей. Удалять старые
  экспорты только после проверки всех consumers. Проверить неигровые/read-only
  использования сетки: replay, summary, catalog не должны получить drag.

В Mushroom уже вызывается core `useTouch` из `web/src/main.js`, а
`web/src/components/prep/BackpackZone.js` передаёт placement preview. Meat
использует configured screen с другим wiring. Поэтому наличия общего
компонента недостаточно: обязательна миграция обоих путей ввода.

## Целевое поведение

### Предметы

1. Тап/клик выделяет предмет в Backpack или Storage и показывает действия.
2. Следующий тап на поле задаёт позицию; отмена снимает выделение.
3. Перетаскивание сохраняет клетку захвата: предмет не прыгает относительно
   указателя. Предпросмотр, проверка и сохранение используют один anchor.
4. До отпускания видна вся форма со snap к сетке. Допустимость обозначена не
   только цветом; конфликтные клетки выделены отдельно.
5. Невалидный drop не отправляет заведомо ошибочное сохранение и оставляет
   предмет на прежнем месте. Рядом с целевой формой появляется «Занято»,
   «Нет клетки рюкзака» или «Выходит за поле».
6. Подсказка остаётся после отпускания достаточно долго для чтения. Начальная
   настройка — около двух секунд; уточнить по проверке на телефоне. Текст не
   перекрывает целевые клетки и не требует закрытия. Повторный отказ обновляет
   подсказку, не создавая очередь сообщений.
7. Возврат в Storage — отдельная кнопка. Авторазмещение — явное действие с
   объяснением отсутствия места. Поворот обновляет форму и допустимость.
8. Ошибка сервера после допустимого preview оставляет подтверждённую раскладку
   и даёт короткое объяснение. Серверная проверка остаётся обязательной.

### Сумки

- В режиме «Переставить сумки» сумки доступны для выбора и переноса прямо на
  поле; обычное управление предметами не должно случайно захватывать сумку.
- Плашки остаются дополнительным способом выбора и доступа к действиям.
- Предложение для первого выпуска: предметы сохраняют абсолютные позиции;
  перенос сумки разрешён, если итоговое покрытие всех предметов сохраняется.
  Иначе подсветить оставшиеся без покрытия клетки и показать «Сначала перемести
  предметы». Решение явно показать в интерфейсе режима.
- Перенос содержимого вместе с сумкой пока отложить: предмет может пересекать
  две сумки, поэтому однозначное владение содержимым отсутствует.
- Проверить существующую политику стартовой сумки. Если она фиксирована,
  обозначить замок и причину; не менять политику молча.

### Поле и доступность

Доступная пустая клетка и пространство вне сумок визуально различаются.
Предпросмотр виден рядом с пальцем; подписи и действия не закрывают цель.
Выбор, размещение, поворот и отмена доступны без drag, в том числе с клавиатуры.
Короткое объяснение отказа доступно вспомогательным технологиям без повторного
озвучивания на каждом движении указателя.

## Этапы и рабочие потоки

Оригинальный исполнитель отвечает за интеграцию, обновление этого плана,
финальные проверки и handoff. При делегировании каждый поток меняет только
свой scope; важные находки переносит в журнал плана.

| Поток | Входы и результат | Write scope | Зависимости | Условие завершения и проверка |
| --- | --- | --- | --- | --- |
| A. Воспроизведение | Отзыв, актуальные базы обоих потребителей → воспроизводимые раскладки и baseline на desktop/mobile | Оба потребителя: fixtures и evidence; core: этот план | Нет | Отдельно проверить стык, настоящую пустоту, точку захвата и управление сумкой; записать подтверждённую причину либо невоспроизведённый сценарий |
| B. Геометрия и допустимость | Раскладки A, валидатор → общий расчёт anchor, footprint, конфликтных клеток и кодов причин | Core: `modules/loadout/`, доменные тесты и публичные типы | A | Тесты покрытия объединением сумок, коллизий, границ и исключения перемещаемой строки; `npm test` |
| C. Ввод и предпросмотр | Контракт B → единое состояние выбора/drag, pointer lifecycle и preview | Core: `vue/composables/`, `vue/configured/`, `vue/components/`, соответствующие тесты | B | Мышь/touch/pen, смещение захвата, отмена, поворот и серверный отказ; устранить двойную обработку native drag и Pointer Events |
| D. Интеграция двух игр | Контракт C → оба prep-экрана на одном контроллере, локализованные подсказки и действия | Meat: product adapters/locales/theme; Mushroom: `web/src` wrappers/locales/theme; без копирования механики | Контракт B/C; интеграция после C | Нет попапов; нет перекрытия цели; проверить русский/английский и узкий экран |
| E. Проверка и handoff | Реализация B–D, сценарии A → parity двух игр, browser evidence и проверка WebView | Meat: `tests/browser/`; Mushroom: `tests/game/`; core: этот план; без исправлений чужого scope | B–D | Выполнить матрицу ниже, сопоставить изображения с описаниями состояний, записать ограничения |

Последовательность: A → B → C → интеграция D → E. После согласования контракта
B продуктовое оформление D и подготовка проверок E могут идти параллельно с C. Перед
параллельной работой выделить владельца каждого файла; shared-компоненты не
редактировать одновременно нескольким исполнителям.

## Проверки и критерии приёмки

- [ ] **AC1** — Предметы 1×2 и 2×2 размещаются через стык соседних сумок, если покрыты
  полностью; наличие одной непокрытой клетки даёт точную подсветку и причину.
- [ ] **AC2** — Захват за разные клетки предмета даёт ожидаемую позицию; preview совпадает
  с сохранённой формой после drop, в том числе после поворота.
- [ ] **AC3** — Можно переместить предмет из Storage в выбранное место drag или двумя
  тапами; тап по размещённому предмету не отправляет его в Storage.
- [ ] **AC4** — Сумку можно выбрать и переместить на поле мышью и пальцем; перенос,
  нарушающий покрытие предметов, блокируется с объяснением до сохранения.
- [ ] **AC5** — Invalid drop, отпускание вне поля, Escape, `pointercancel`, потеря capture
  и уход со страницы не меняют подтверждённую раскладку и не оставляют ghost.
- [ ] **AC6** — Прокрутка экрана доступна вне активного drag; drag не запускает
  случайный click, удаление или повторный API-запрос.
- [ ] **AC7** — Нет места для авторазмещения — видимое объяснение; ошибка API — прежнее
  состояние и понятная подсказка; быстрые повторные действия не теряют revision.
- [ ] **AC8** — На узком экране подсказки, поворот и режим сумок доступны, не перекрывают
  цель; причина понятна без различения красного и зелёного.
- [ ] **AC9** — Проверены desktop mouse, браузер touch viewport, iOS Telegram WebView и
  Android Telegram WebView. Эмуляция viewport не заменяет реальный WebView.
- [ ] **AC10** — Tutorial обновлён под выбор/размещение: текст и anchors соответствуют
  действиям. Бой начинается с сохранённой раскладкой, статистика не расходится.

Все критерии выше обязательны для обеих игр. Дополнительно:

- [ ] **AC11** — Обе игры используют один controller core и одинаковую модель причин
  отказа; у продуктов отсутствуют дублирующие вычисления anchor/coverage.
- [ ] **AC12** — Два одинаковых предмета перемещаются независимо по instance ID.
- [ ] **AC13** — Различия в каталогах и политиках заданы конфигурацией, а не fork механики.
- [ ] **AC14** — Покупки, undo, fusion, tutorial, хранилище и начало боя сохраняют свои
  действующие контракты; сохранение переживает refresh в обоих продуктах.
- [ ] **AC15** — У каждого изменённого UI есть свежие mobile 375×667 и desktop 1280×800
  снимки и исполняемые проверки геометрии/неперекрытия действий.

Добавить целевые доменные тесты и browser-сценарии взаимодействия, а не только
проверку количества предметов. Использовать `data-testid`. Для evidence
сохранять состояние и viewport в описании каждого снимка; перед чтением
применять hub `shrink:screenshots`.

После core-изменений: `npm test`; при изменении публичных экспортов/пакета —
`npm pack --dry-run`. После интеграции Meat: `npm run game:test`,
`npm run game:test:browser`, `npm run game:build`. Перед релизом —
`npm run game:deploy:check` с требуемой конфигурацией. Для Mushroom: `npm run game:test`, `npm run game:test:e2e`,
`npm run game:test:screens` и `npm run game:build`; перед добавлением E2E читать
`docs/user-flows.md` и обновлять изменённые шаги. Для UI соблюдать локальные
layout assertions и proof loop с AC-ID/evidence. Two-consumer gate запускать
на согласованных pointers: hub `npm run verify:backpack-core`.

## Порядок поставки

1. План привязан к issue #5 с критериями для обеих игр. Перед реализацией
   выбрать согласованные чистые базы core, Mushroom и Meat и повторить этап A.
2. Реализовать общую механику в core через публичные фасады. Не копировать
   обработчики в Meat; продукт передаёт тексты, тему и настройки.
3. Протестировать, commit/push core и открыть PR. PR не мерджить.
4. Интегрировать один проверенный core commit в Mushroom и Meat. Проверить
   оба продукта, обновить тексты/tutorial/user flows. Mushroom следует локальному
   direct-to-main workflow; Meat — feature branch/PR. План не требует менять
   Git-политику потребителей. Сначала добиться parity обоих, затем поставлять
   consumer commits; не считать один улучшенный продукт завершением задачи.
5. Передать пользователю ссылки, evidence и известные ограничения. Порядок
   поставки: core → Mushroom/Meat согласно их Git-политике. Не заявлять поддержку реальных
   WebView без проверки на устройствах.
6. После пользовательского merge и проверки base commits обновить hub pointers
   стандартными помощниками; затронуть только нужные pointers на hub `main`.
